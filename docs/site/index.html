A TPU inside Qwen's weights.

A weight-stationary matrix-multiply array compiled into a stock Qwen3_5ForCausalLM. The weight matrix lives in Gated DeltaNet state, the multipliers and requantiser are SwiGLU layers, and each layer's output token is the next layer's input. No training. No external runtime.

Why would anyone put a TPU inside a language model?

Airplanes do not flap their wings. Nobody needs a TPU inside Qwen: a real TPU is faster, cheaper and does not lose its arithmetic to a rounding error. So why do it?

Because the bird teaches you something

A language model is a pile of memory (state), a way to look things up (attention) and a way to compute (FFNs). If that is enough to build an exact matrix-multiply machine, then we learn how much of "intelligence hardware" is hiding in the architecture itself. We are studying the bird, not selling the wing.

Because exactness is a hard test

Models are sloppy by design. Making every integer survive bf16 rounding, normalisation and a couple of dozen layers of someone else's code is a very unforgiving way to find out what the architecture really does.

What we do not claim

Not the first machine in Qwen's weights (Qwenputer and QwenPU got there first). Not faster than a real accelerator, or than QwenPU at the op level. Not useful for production. It is an existence proof, with receipts.

Why a Gated DeltaNet head is already a dataflow array

A TPU keeps weights put, streams activations, and accumulates partial sums in place. DeltaNet state S is a matrix with exact row write and row read.

One-hot write = store a row

With α=β=1 and a one-hot key, S += k(v − Sᵀk)ᵀ replaces row i exactly. That loads a weight row, or stores a partial sum.

Multi-hot read = adder tree

A multi-hot query returns the exact sum of the chosen rows. The contraction over the inner dimension is one read.

Counts, not values

Products are bit-ANDs, so accumulators hold small integer counts that bf16 stores exactly. The weighted sum is a free linear form.

Architecture

Qwen's own layers are muted for chip tokens. The appended TPU layers hold the array. The model's sampled token goes back in as the next layer's activation.




Fine print. Qwen l2-normalises the query and scales it by 1/√(nq·128). A multi-hot query is therefore padded to nq = 2odd rows so that scale is an exact power of two. Otherwise bf16 rounds each count differently (a count of 7 comes back as 6.96875).

Tokens are the bottleneck (packing)

A language model takes one token per step, and every step is a full trip through every layer. Our first array spent one token per input row and one per output column: KR + NC tokens for KR × NC multiply-adds. That is a delivery truck making one trip per parcel.

Packing loads the truck. An ACT token now carries g activations and a READ token reads h columns and answers with one OUT token carrying h outputs. Tokens per matvec fall from KR + NC to KR/g + NC/h.

The price is real: every column now keeps g copies of its weight head and g accumulator heads, a layer only has 16 key heads, so you need more layers, and the vocabulary balloons because one ACT token can mean any of 8g things. MACs per token go 4 → 8 → 16 on 8×8, 32 on 16×16, 64 on 32×32. Every packed configuration is exact in the float64 evaluator and on real Qwen (0 mismatches). Try the packed presets in the stepper above and watch the token counter.

Skip the muted layers (chip-only path)

Qwen's own layers are muted for chip tokens: their attention output is exactly zero and their MLP sees a zero vector. A layer that adds nothing to the residual stream is the identity. So why walk through 24 of them to get nothing?

ChipPath goes straight from the embedding to the appended TPU layers, then the final norm, then only the chip rows of lm_head. It returns the same bits as the full model (a test checks that) and never touches Qwen's cache, so there is nothing to restore afterwards. It is the shortcut through a building where every corridor you skip is empty.

DeltaNet state as RAM

The recurrence S = αS + k(β(v − Sᵀk))ᵀ, o = Sᵀq, read as memory operations.

Does it work on your GPU? (hardware matrix)

Exact integer arithmetic on bf16 hardware is a statement about a software stack, not about the maths. Different chips and libraries add numbers in different orders, and bf16 only has 8 bits to spare. So we replay the same traces on many devices and count mismatches against NumPy. Dashed cards have not been run yet, and we say so.

Bug museum

Two exhibits, both of the form "the answer is off by a hair". Neither was our arithmetic. Both were somebody else's rounding.

  • Exhibit A. Qwen normalises the query and scales it by 1/√128. Pad our multi-hot query to nq = 2odd rows and that scale is a clean power of two; otherwise a count of 7 comes back as 6.96875.
  • Exhibit B. On an L4, cuBLAS sliced the long dot product (split-K) for 288 and 320 token traces and rounded the partial sums to bf16. Setting allow_bf16_reduced_precision_reduction = False keeps the reduction in fp32.

  • New, to my knowledge (one search): a TPU-style dataflow machine with no PC or ISA; the DeltaNet multi-hot read used as a reduction; weights and partial sums both in state; bit-plane counting that keeps every value bf16-exact; layers chained through the model's own tokens.
  • Not new: putting a machine in Qwen3.5's weights, or running a neural network on it. The ballast-normalised RMSNorm, DeltaNet-rows-as-RAM and token-trace ideas come from Qwenputer.
  • Not claimed: faster than QwenPU at the op level (its matvec streams 64 lanes per token; mine does 4 to 16 MACs per token). The scaling is O(N) tokens for O(N²) MACs, not a speed record.
  • TinyTPU is the model for the dataflow idea (stationary weights, streamed activations, in-place accumulation). No code or RTL is shared, and our array is not literally systolic: all columns work in parallel through separate heads.
